# Telegram 机器人

**`careersgftv_bot`，在 `telegram-bot/` 里，
它是这个项目里唯一不在 Vercel 上的部分。**
它跑在一台 Debian VPS 上、在 tmux 底下，来自同一个代码库，
部署方式是手动拉取并重启那个进程。

`telegram-bot/README.md` 是它的说明文件，`setup.md` 涵盖 BotFather 那一边。
这一页说的是它的形状，以及那些会让人栽跟头的东西。

## 它是什么，不是什么

**一条投递通道，以及一个第二因素。**
它绝不是任何东西的唯一记录：
一个没有绑定 Telegram 的申请人，
在入队平台上仍然看得到每一份邀请和每一件待办事项。

- 从任何一端把一个 Telegram 账户绑定到一个入队平台账户。
- 投递六位数字登录验证码，
  或一条绑定在提出请求的那个浏览器上的一键登录链接。
- 在申请人打开它之后，在登录时充当第二因素。
- 投递三种通知，每一种都可以单独开关。

**九个指令，而且只有九个。**
这里没有 `help`；`start` 带着那些内容。
`telegram-bot/commands.py` 是那份列表的唯一副本。
Telegram 注册的菜单、start 讯息、`setup.md`
和[指令参考](/bot/commands)全都来自它。
`python commands.py --check` 会证明那几份文件仍然一致。

## 网站从不调用机器人

**入队平台往 `gftvjobs_notifications` 写一笔记录然后就返回。**
机器人轮询那张表、认领一批、送出，
并把每一笔标记为已送出或失败。

**安全讯息是直接送出的，而且无法关掉。**
密码变更不是任何人可以选择不接收的通知。

**两个循环，差别在于谁在等。**
登录验证码每两秒轮询一次，因为有人正坐在登录表单前面。
发件箱每二十秒轮询一次，因为一份邀请等得起。
两者用的是同一套条件式认领，所以两个实例不可能同时送出。

## 登录验证码从哪里来

**是机器人生成的，那和规格书读起来的样子不一样。**
说明书写的是入队平台送出六位数字验证码，而入队平台做不到：
网站那一边没有任何东西联系得上 Telegram。

所以网站写下一笔意思是「有人索取了验证码」的记录，
把哈希字段设成一个待处理标记外加一些随机内容。
机器人用一次条件式更新认领一批，生成那些数字、
把 bcrypt 哈希写回去，然后送出讯息。
**那个验证码只存在于一个进程和一则聊天讯息里。**

**一键登录链接只会为一个来自浏览器的请求制作。**
网站会在 cookie 里设一个一次性随机值，并把它的哈希存在那一笔记录上。
只有那个哈希在的时候，机器人才会制作链接。
在聊天里打出来的验证码背后没有浏览器，
所以它拿到的是数字，没有链接。

> [!WARNING]
> 机器人的 bcrypt 必须和网站的一致，两边都是成本 12。
> `tests/phase11-test.mjs --only=seam` 检查的正是这一点，
> 对照的是一个真实的 Python bcrypt 产生出来的哈希。
> 它防止的那种失败，是一个正确的验证码在登录表单上被拒绝，
> 而任何日志里都没有东西可以解释它。

## 部署它

```bash
cd telegram-bot
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # fill it in
python bot.py
```

部署一次改动就是 `git pull`、
在那个文件有变动时跑 `pip install -r requirements.txt`，然后重启。

> [!DANGER]
> **任何跨越两边的改动，顺序都很重要。**
> 网站那一半在合并时会自行部署；这一半不会。
> 请先拉取并重启机器人，再合并，
> 否则入队平台会提供一个控件，通往一个跑着上周代码的进程。

**第二个实例会拒绝启动。**
它不会等待，也不会去抢那把锁。
它会印出持有 `bot.lock` 的那个进程编号，并以状态 3 退出。
所以「旧的那个确实死了吗」是一行输出，而不是一个判断题。

| 退出码 | 意思 |
|---|---|
| 0 | 干净地关闭。 |
| 2 | 环境不可用。它会列出环境里的每一个问题。 |
| 3 | 已经有另一个实例在运行，并写明它的进程编号。 |
| 1 | 其他任何情况，日志里带着堆栈追踪。 |

## 它自己的惯例

- **Telethon 和 Python。**
  不是 python-telegram-bot，也不是 aiogram。
- **任何属于机器人本地的东西都用 SQLite**：
  排程、速率限制、去重，
  以及一份记录每个按钮代表什么意思的登记，好让按钮在重启之后仍然有效。
  请储存那个负载并在点击时查它；绝不要把状态塞进回调数据里。
- **Supabase 是共享的事实来源**，
  用于账户、绑定、令牌、邀请和发件箱。
  SQLite 绝不重复保存账户数据。
- **绝不要在回复里提到机器人自己的名字。**
- **使用富格式回复**，而且不用长破折号。

**它会从上线中的网站读取 `build-status.json`。**
一个还没做好的指令会用阶段那句话回复，
一个被关掉的指令会用维护那句话回复。这两者绝不混用。

## 状态探针

**`probe.py` 不是机器人的一部分。**
它是一个碰巧住在同一台机器上的独立进程，和 Telegram 毫无关系。

**一个托管在它所监控的东西上的状态页面，
在它存在所要汇报的那次故障期间是没有用的。**
这台 VPS 是整个架构里唯一在 Vercel 之外的组件，所以探针跑在这里。
每分钟四次公开的 GET，
透过那个拥有那些表的唯一函数直接写进 Supabase。

**一个联系不上 Supabase 的探针什么都不写，也什么都不说。**
它不会重试成一堆积压，也不会缓冲。
数据里的一段空白是一段诚实的空白，而页面会把它画成没有数据。

## 它完全没有脚本化的检查

**那是刻意定案的。**
取代一套测试套件的，是 `telegram-bot/README.md` 里那份手动检查清单，由一个人走过。

**`LOG_LEVEL` 是您用来代替一次测试运行的东西。**
走那份检查清单时该伸手去拿的是 `DEBUG`，而那不是该一直开着的设定。
