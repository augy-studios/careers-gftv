# 数据库

**一切都跑在既有的国际兽视 Supabase 项目里，在 `public` 模式底下。**
不要建立新项目，也不要建立新模式。
本项目的表和 gftv.asia 拥有的 `gftvhello_*` 表并列在一起。

**存取只在服务器端**，从 Vercel 函数出发，使用服务角色密钥。
任何地方都不使用 Supabase Auth。
浏览器从不和 Supabase 对话，也从不收到 anon 密钥。

## 行级安全，而且没有策略

**每一张 `gftvjobs_*` 表都启用了行级安全，而且完全没有策略。**
服务角色会绕过行级安全，
所以入队平台照常运作，而任何持有 anon 密钥的东西什么都拿不到。

这一点很重要，因为这个项目和国际兽视其他应用共用，
而它们的 anon 密钥就是同一把 anon 密钥。

> [!WARNING]
> 视图以它的拥有者身份运行，所以它底下的行级安全并不适用。
> 迁移 `035` 把那四个视图从 `anon` 和 `authenticated` 收回，
> 并设定 `security_invoker = on`。
> 在它之后建立的每一个视图，都在建立它的那个文件里遵循同一条规则。
> 函数也需要同样的处理：`037` 收回自己的权限，再按名称授予 `service_role`。

## 两个命名空间

| 前缀 | 属于谁 | 本项目可以做什么 |
|---|---|---|
| `gftvjobs_` | 本项目的 | 任何事。 |
| `gftvhello_` | gftv.asia 平台的 | 只读，此外什么都不做，例外见下。 |

**`gftvhello_*` 那些表绝不从这里建立、修改或删除。**
它们只被外键引用。
登录流程正当拥有的，是它为自己写入的那些挑战、受信任设备和备用码记录。

**有两个字段是被指名的例外，而且没有第三个。**
两者都是刻意要求的，而且都从同一个文件写入，
也就是 `api/_lib/staff-account.js`，好让第三个必然会是有人审阅的一次 diff。

| 字段 | 由谁要求 | 它的代价 |
|---|---|---|
| `password_hash` | 5g | 在这里设定的员工密码就是 gftv.asia 的密码。 |
| `totp_secret` | 5f | 在这里新增或移除验证器应用，在 gftv.asia 也一样。 |

如果有第二个文件写入那张表，或者那一个文件写入了第三个字段，
`node tests/phase13-test.mjs --only=account` 就会失败。

## 迁移

**所有的 DDL 都是 `migrations/` 里编号的 SQL 文件，手动贴进 Supabase 的 SQL 编辑器。**
没有命令行工具、没有执行器，也没有框架。
每一个文件和它做什么，都列在 `migrations/README.md` 里。

有两条规则比其余的都重要：

- **绝不要编辑已经运行过的文件，也绝不要重新编号。**
  一次改动会变成一个新的编号文件。
  这在构建期间也成立，因为生产环境从第 3 阶段起就一直上线着。
- **第 1 阶段的整套文件在第一天就全部运行了**，
  所以数据库跑在界面前面。
  一个在稍后阶段才打开的功能，不需要新的 SQL。

### 写一个迁移

六个性质，而这个目录里的每一个文件都具备这六个。

1. **编号** `NNN_description.sql`，补零，按数字顺序运行。
2. **包在 `begin` 和 `commit` 里**，这样中途失败什么都不会留下。
3. **幂等**，这样在您搞不清楚状况时重跑一次是安全的。
4. **在最后记录进 `gftvjobs_migrations`。**
   那张表是什么已经运行过的唯一记录。
5. **在底部带着一段被注释掉的回滚区块。**
   撤销一个迁移是复制粘贴，绝不是重新构思。
6. **对任何新表启用行级安全，而且不加策略。**

```sql
select filename, applied_at from gftvjobs_migrations order by filename;
```

**如果一个文件出错，它里面的任何东西都没有被套用。**
修好原因，再把同一个文件跑一次。

**回滚区块是刻意注释掉的。**
取消注释、读清楚它会丢掉什么，然后再运行。
其中有几个会在依赖的记录还存在时拒绝执行，那是有意为之。

### 关于顺序的一条规则

**一个会改变「登录状态是什么」的迁移，要排在读取它的代码之前。**
迁移 `038` 把入队平台的员工登录状态搬进本构建拥有的一张表，
而套用它会让每一位员工被退出登录一次。
那和这次构建里其他所有东西的顺序相反，而那个文件也这样写着。

## 什么由 Postgres 拥有，而不是应用代码

**搜索向量和标签计数由触发器维护**，写在迁移 `009` 里，此外没有别的。
那是刻意的：
一则直接在 Supabase 表格编辑器里编辑过的职位，仍然搜索得到，标签计数也仍然诚实。

**不要从 `main-site/api` 写入 `gftvjobs_jobs.search_vector`
或 `gftvjobs_tags.usage_count`。**

**加权搜索、摘要片段和三元组回退都是 Postgres 函数**，
用 `supabase.rpc()` 调用。
它们用 PostgREST 的筛选条件很难表达，
这正是它们是函数而不是查询构建器的原因。

## 首次运行前值得知道的两件事

**`gftvhello_users.id` 必须是 `uuid`。**
有好几张表对它有外键，
如果它原来是别的类型，有四个迁移会在那个键上失败。

**有五张表不在规格书第 6 节里。**
稽核日志、设置、cron 运行记录、速率限制，以及权限覆盖层，
它们之所以存在，是因为说明书要求的行为无处安放。
`012` 的头部注释写明了每一张背后对应的是哪一节。

## 唯一从 Vercel 之外写入的东西

**`gftvjobs_status_days` 和 `gftvjobs_status_incidents`**
由 VPS 上的 `telegram-bot/probe.py` 透过 `gftvjobs_status_record()` 写入。
`main-site/api` 里没有任何东西写它们：
状态页面读它们，每日的 cron 在九十天时清扫它们。

**两者刻意都不带外键。**
它们是关于某个地址在某一刻的观察，
而且必须在入队平台对一切都回应 500 的时候仍然写得进去。
