# 规格书

**`careers-gftv-spec.md` 是整个项目的说明书。**
它放在代码库根目录，已提交，而且是每一个阶段的参考依据。
它大约有一千七百行，里面的细节都是承重的。

需要放慢速度读的是第 6 节（数据库结构）和第 5 节（身份验证规则）。
其他所有东西都建立在这两节正确的基础上，
而日后重做其中任何一节，都意味着要动到它之后的每一个阶段。

## 它涵盖什么

| 节 | 内容 |
|---|---|
| 0、0b、0c | 先读什么、十五个阶段，以及公开发布。 |
| 1、2 | 在建造什么、技术栈，以及代码库的惯例。 |
| 3 | 设计，包括 3a 的多语言规则。 |
| 4 | 公开网站：职位板、职位页面、数据源，以及可被发现性。 |
| 5 | 身份验证，分七个带字母的小节，包括谈通行密钥的 5e。 |
| 6 | 数据库：每一张表、索引、触发器和函数。 |
| 7 | 申请流程，分九个带字母的小节。 |
| 8 | 员工管理后台，逐区块说明，另有谈手册的 8a。 |
| 9 | API 设计及其响应封装。 |
| 10 到 15 | 已定案的决定、维护、webhook、离线，以及机器人。 |
| 16 | 这个说明文件网站，包括列出页面清单的 16h。 |
| 17 | 交付物。 |

## 最重要的那条规则

**凡是规格书和其他任何东西不一致的地方，都要问。**
说明书在第七行就写了这一点，而且它是认真的：不要默默挑一边。

那包括这本指南、两份 README、代码里的注释，以及构建产出的任何文件。
规格书是参考依据，它不一定是最近有人写下的那份东西。

> [!TIP]
> 提供选项和一个建议，让拥有这个项目的人来选。
> 正是那个习惯产生了工作备忘里的每一条偏离记录，
> 也是那些决定日后还读得回来的唯一原因。

## 当说明书被修订时

**这种事会发生，而且是刻意做的。**
从这次构建里举三个例子，每一个的日期和理由都写进了说明书本身：

- 第 7i 节说只有管理员可以把翻译标示为就绪。
  有四个界面字符串却向帮手承诺了同样的事，而那些路由允许任何员工去做。
  说明书被修订了，因为一条被界面推翻的规则，是没有人在遵守的规则。
- 第 3a 节里写着入队平台的华文名称。名称改了，3a 也就跟着改。
  一次说明书仍在推翻的更名，不算真的更名。
- 第 10 节第 1 项说不使用 Supabase Storage、不允许上传。
  每个账户一张方形头像是被记录下来的例外，
  它写在 `main-site/AVATARS.md` 里，读到上传相关内容的人会在那里找到它。

**不是每一处不一致都会修订说明书。**
有时行为是以另一种方式定案的，而读者看到的东西并没有错。
那样的冲突会记在工作备忘里，说明书本身不动。
那是一个判断，而且是应该交给项目拥有者、不该自己做的判断。

## 在这里阅读它

**这份说明书会在本站重现**，因为这个项目拥有那个文件，没有别的地方持有它。
它会以这一区块底下的页面呈现，文件的每一个顶层小节各一页。
它们由文件本身生成，所以两者不可能漂移。

> [!NOTE]
> 生成器是这一部分构建的后半段，会和那些页面一起交付。
> 在那之前，代码库根目录的那个文件是唯一的副本，也是该读的那一份。

**有两个文件刻意不在本站任何地方重现。**
`gftv-theme.md` 和 `gftv-official.md` 在国际兽视各代码库之间流通，
所以本代码库里的那两份本身已经是副本了。
各自规范什么请看[主题](/staff/developer/the-theme)
和[官方横幅](/staff/developer/the-official-banner)，正文请到源头去读。
