# 多语言层

**英文以来源语言的身份住在基础记录上，其他每一种语言都是翻译表里的一笔记录。**
整个形状就是这样，规格书第 3a 节是参考依据。

入队平台今天有英文和简体华文，一次只显示一种。
两者都是完整的：每一则职位、每一个界面字符串，以及整个管理后台，两种语言都有。

## 内容：两张表，一个标记

| 部分 | 住在哪里 |
|---|---|
| 来源 | 基础记录，英文，在 `gftvjobs_jobs` 及其相关表上 |
| 其他每一种语言 | 对应翻译表里的一笔记录，以语言代码为键 |
| 启用中的语言 | `gftvjobs_locales` |

**只有在 `is_ready` 被设定时，翻译才会显示**，
所以一份未经审阅的翻译可以待在表里而不上线。

**一则职位可以在完全没有翻译的情况下发布。**
它会以英文显示，并附上说明。
一份翻译至少要有标题，否则无法显示。

**短代号永远不翻译。**
标签和部门的短代号是网址标识，
翻译其中一个，会在有人切换语言的那一刻弄坏每一条分享出去的链接。

## 界面字符串：两个字典

`main-site/assets/i18n/en.json` 和 `zh.json`，扁平的点分键，
本站也有对应的一对。新增或更改一个字符串：

1. **把键加到两个文件里。**
   英文是那个后备层，所以 `zh.json` 里缺少的键会渲染成英文。
   `en.json` 里缺少的键会渲染成那个键本身。
2. 用 `data-i18n` 引用文字、用 `data-i18n-attr` 引用属性，
   或用 `data-i18n-html` 引用含链接的字符串。
3. **把英文留在标记里**，作为元素自己的内容。
   它是没有 JavaScript 时的后备，也是字典解析完成之前显示的内容。
4. `{placeholders}` 必须在两个文件之间一致。
5. 运行 `node check-i18n.js`。

> [!WARNING]
> `data-i18n-html` 之所以安全，唯一的原因是它渲染的每一个字符串都来自这些文件。
> 绝不要把它指向任何用户可以写入的东西。

**缺少的键会在画面上渲染成它自己的名字**，两种语言都一样。
那个后备是刻意的，
因为一个缺失的字符串应该降级成某个搜索得到的东西，而不是一个空元素。
那也是为什么有一个键在页尾读起来像它自己的名字，整整撑过了十一个阶段。

有两样东西会抓到它，而且两者都抓不到另一种失败。
`check-i18n.js` 会读取每一个属性和每一次字面调用，
并在遇到 `en.json` 里没有的键时以非零状态退出。
`t()` 会对每个键在控制台警告一次。
**两者都看不到的，是在字典载入之前由 JavaScript 写出的字符串。**
任何在翻译流程之外调用 `t()` 的东西，都必须在语言变更事件时重绘。

## 这里的华文是新加坡华文

国际兽视是新加坡的组织，而文件标注为 `zh-Hans-SG`。
用词规则就是新加坡读者所预期的那些，
它们连同例子列在翻译指南的[新加坡华文](/translations/singapore-mandarin)那一页上。

**不要用手去对照那份列表检查新写的文案。**
那份列表本身是 `gen-review.js` 里的 `USAGE`，而且那是唯一的副本。
审阅页面的说明就是从它写出来的。
`node check-copy.js` 会拿它去衡量这次构建里的每一个字符串，
而 `tests/phase12-test.mjs --only=zh` 衡量其余的部分。

**每一位读者自己系统的字体会绘制这些汉字。**
`theme.css` 里没有指定任何中日韩字体，
所以汉字会越过那些拉丁字体族，落到平台默认的那一个。

> [!DANGER]
> 让那件事正确的是 `lang` 属性，不是字体堆栈。
> 汉字和日文共用。
> 一个没有语言可以依据的浏览器，
> 可能会挑一个日文字体，把其中不少字画成不一样的形状。
> 每一页都在绘制前的脚本里设定 `lang="zh-Hans-SG"`。
> 如果哪一天它不再被设定，华文就会以错误的字形渲染，而其他东西看起来都没问题。

## 语言不在网址里

它住在 `localStorage` 里，而那有三个后果，
值得在有人把其中之一当成缺陷回报之前先知道：

- **一条分享出去的链接，会以收件人保存的语言打开。**
- **搜索引擎只会看到英文**，
  所以网站地图和结构化数据描述的只有英文。
- **链接预览一律是英文**，因为爬虫没有 `localStorage` 可以读。
  安装用的 manifest 也是一样。

## 搜索因语言而异，而且必然如此

**Postgres 无法切分汉字。**
一串汉字对 `to_tsvector` 来说是一个词元，
所以搜索一个词的一部分永远不会匹配。
能修好它的那些扩展在 Supabase 上没有。

| 语言 | 怎么匹配 | 读者得到什么 |
|---|---|---|
| 英文 | 迁移 `009` 产生的加权 `tsvector` | 按相关度排序，附高亮片段 |
| 其他所有语言 | 对生成的 `search_text` 字段做三元组匹配 | 所有包含输入内容的结果，按标题接近程度排序 |

**两者都能用，只是英文才排得好。**
那一点完整地写在 `migrations/README.md` 里，
因为从外面看它像一个缺陷。

## 新增一种语言的代价

**`gftvjobs_locales` 里的一笔记录、一个字典文件，以及内容本身。**
不需要迁移，也不需要修改数据库结构。

不免费的是它周围的一切：

- 两个网站字典里的每一个界面字符串，而且键要对齐。
- 每一则职位、部门和标签的翻译，都得有人去写。
- 由一位读得懂那种语言的人通读一遍，
  而那正是 `node gen-review.js` 会建出一个页面来支持的事。
- **服务工作线程会预先缓存那些字典**，
  所以新增一种语言就是改变了被缓存的内容，也就要跟着提升一次 `VERSION`。

## 审阅页面

```sh
node gen-review.js
```

它会写出 `zh-review.html`，
把这次构建里每一个华文字符串放在它的英文旁边，让一位流利的读者逐条看过。
那包括各个字典、写入的部门和标签、首页文案、阶段列表，
以及机器人的讯息和简介文字。

**它也会在遇到任何一个带汉字、却不在它两份名单上的文件时失败。**
下一个把华文摆到读者面前的文件，不可能默默错过这次往返。
它的输出被 git 忽略：请重新生成它，不要把它提交上去。

它读取机器人的字符串是靠引入那些 Python，绝不是靠解析它，
所以它需要 Python 在路径上。
