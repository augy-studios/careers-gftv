# 服务工作线程

**两个网站、两个工作线程，以及一条对两者都适用的规则。**

> [!DANGER]
> **那个网站每有一次改动，就把 `sw.js` 顶部的 `VERSION` 提升一次。**
> 不是每个阶段一次，也不是只有工作线程本身改动时才提升。
> `main-site/` 底下的任何一次编辑都是一次新的构建。
> 一个没有被提升的工作线程，会继续把上一个构建服务给每一个来过的人。
> 那样，一次已发布的改动，正好对回访最勤的那些人是隐形的。

`vercel.json` 在两个网站上都以 `Cache-Control: no-cache` 提供 `sw.js`，
所以浏览器一律会重新抓取它。
但那个文件本身仍然必须有所不同，那才会起作用。

## 入队平台的工作线程

`main-site/sw.js`。
在第 10 阶段之前它是刻意的直通，现在它会用下列其中一条路径回应每一个请求。

| 请求 | 会发生什么 |
|---|---|
| 导航到一个已预先缓存的路由 | 缓存里的外壳，完全不走网络。 |
| 导航到 `/status` | 网络优先，只有失败时才用缓存副本。 |
| 导航到 `/jobs/{id}` | 陈旧内容边用边更新，上限 100 则职位。 |
| 其他任何导航 | 走网络，失败时给 `/offline`。 |
| `/assets/**`、各个图标、manifest | 缓存优先。 |
| `/api/public/**` | 陈旧内容边用边更新。 |
| `/api/public/feature-status` | 只走网络，并在经过时读取它。 |
| `/api/` 底下的其他任何东西 | 只走网络，绝不缓存。 |
| 任何跨源请求 | 完全不拦截。 |
| 任何不是 `GET` 的请求 | 完全不拦截。 |

### 四条很容易被破坏的规则

**带着 `private` 或 `no-store` 的响应绝不会进入 Cache API。**
有两条路由会那样回应已归档的职位和员工预览，
而从工作线程内部看，两者都和公开路由长得一模一样。
`isCacheable()` 是做那个判断的唯一地方。

**跨源的东西一律不拦截**，
这也是 Storage 上的头像不会进缓存的原因。
管理后台会渲染别人的面孔。

**`skipWaiting` 和 `clients.claim` 只在有人要求时才调用。**
两者都不出现在 `install` 或 `activate` 里。
读者接受更新提示时，页面会发送 `skip-waiting`，那是通往这两者的唯一路径。

**外壳缓存带版本，数据缓存不带。**
一次 `VERSION` 提升，就是一个从网络填充的新缓存，加上丢掉旧的那一个。
职位缓存和公开回答缓存会活过它。
每次部署都把它们清空，会在读者刚好离线的那一刻清空整个职位板。

### 预先缓存列表

**它是这个网站里最危险的对象。**
发布前请跑 `node check-precache.js`，就像您跑 `check-i18n.js` 一样。
它会用 `cleanUrls` 的方式解析每一个条目，并在有条目不在磁盘上时以非零状态退出。

那份列表是一次加一个条目，绝不透过 `cache.addAll`。
那个方法在第一个坏路径上就整体拒绝：
安装失败，而每一项离线行为都默默地被关掉了。
两相比较，一个错误的条目只损失一个文件，而且它会说出来。

### 两个紧急开关

`offline` 和 `install` 是第 10 阶段的功能键，
所以管理员可以从维护页面翻转其中任何一个。
工作线程会从每一页本来就会抓取的那个功能状态响应里读出答案，
并保留它最后看到的那一个。

**两者都是双向的，而有两件事对此是承重的。**
一个无法撤销的开关不是开关。
它之所以存在，正是因为有一个工作线程在别人的手机上出了问题。

- **那个功能状态请求的处理位于紧急开关之上。**
  如果它像其他东西一样直接短路到网络，
  工作线程就会在它被关掉的那一刻停止倾听。
  那样就没有管理员能把它重新打开。
- **缓存是在边缘被丢弃并重新填充的**，不是每个请求一次。
  每个请求都丢弃，会和重新打开时启动的那次重新填充产生竞争。

## 本站的工作线程

`docs-site/sw.js`，自第 14 阶段第 4 部分起。
**入队平台的工作线程并不是它的模板。**
那个文件是一个操作队列、一个职位缓存和那些维护开关，这里一样都没有。
这一个有层级，而入队平台没有对应的东西。

**预先缓存列表不需要您维护。**
`scripts/build.js` 会用它刚刚构建出来的那些页面，把它写进 `dist/sw.js`，
所以新增一本指南没有什么要记得的。
`node check-precache.js` 会检查两边，
并在 `dist/` 不存在时用一句话跳过这一边。

| 什么 | 策略 |
|---|---|
| 指南、搜索索引、每一个 API 回答 | 网络优先。 |
| `/assets/*`、字体、图片 | 缓存优先。 |
| `/api/auth/*` | 两个方向都绝不缓存。 |

**读者会阅读的东西一律网络优先**，那是本站据以运转的那个决定。
在步骤已经改变之后，还从缓存里端出一套流程，那才是值得据以设计的失败。

**受闸门保护的指南会被缓存，按读者区分，而那需要小心。**
缓存以它被填充时的层级命名。
外壳在每一次载入时都会发送层级，
而工作线程会丢掉任何不是当前层级的受闸门缓存。
退出登录时会发送 `signed-out`，工作线程就会把它们全部删除。

> [!WARNING]
> 改动那两条路径中的任何一条，
> 都会改变一台共用机器在某人退出登录之后还留着什么。
> 那正是它当初是一个决定、而不是一个默认值的原因。

**这里没有 `/offline` 页面。**
外壳就是那个后备，所以一个没被缓存的地址会画出外观，并说明这一页无法取得。
读者分辨不出一个缺失的页面来自哪一条流水线。
那是那条规则在最容易被破坏的情况下仍然成立。

## 客户端那一半

`main-site/assets/js/connection-bar.js` 注册那个工作线程、
拥有更新提示，并画出那条横幅。
它是共用的：`gen-docs-lib.js` 把它复制过来，
而两个网站有差别的那三个地方是参数，不是编辑。

**那条横幅有三种状态，但只有一条横幅。**
离线的优先级高于联系不上网站，
后者又高于有更新，因为两条横幅叠在一起就不再是不打扰人的了。

| 状态 | 什么时候 | 可否关闭 |
|---|---|---|
| `offline` | `navigator.onLine` 为 false | 不可以。网络恢复时它会消失。 |
| `unreachable` | 在线，而且连续两次 API 调用都失败 | 一样不可以。 |
| `update` | 有一个新的工作线程在等待 | 可以，对那一次页面浏览有效。 |

**关于连线的那两种措辞是重点，不是锦上添花。**
`onLine` 为 false 是一句可靠的「确实没有网络」。
`onLine` 为 true 只代表某个接口是通的，
所以在完好的无线网络上发生的一次故障，读起来会是在线。
一条写着「您目前离线」的横幅，会把那位读者送去重置一台好好的路由器。

## 申请人自己的数据

**任何经过验证的东西都不会放进 Cache API。**
申请人收藏的职位、申请、待办事项、个人资料和头像，
改为住在 IndexedDB 里，在 `assets/js/idb.js`。

- **用户编号是键的一部分**，不是它旁边的一个字段。
  即使清除失败，为某个申请人做的一次读取也不可能返回另一个人的记录。
- **一个 null 的登录状态会清除；一个失败的不会。**
  在没有网络时，那个请求每一次都会失败。
  把它当成退出登录，等于在离线副本是唯一一份副本的那一刻把它丢掉。
- **每一个函数都安静地失败。**
  IndexedDB 在某些隐私浏览模式里无法使用，
  所以读取会返回 null，而写入什么都不做。

## 操作队列

**只有两种操作，不会再多**，两者都来自那个交接对话框：
评分，以及那个是或否。
在请求因网络错误而失败时排队，并在网络恢复时送出。

**排队中的回答是待处理，不是已完成。**
再次申请的冷却期绝不会由一笔本地队列记录启动，
而申请控件正是为此有一个 `queued` 状态。

**每一个操作都是幂等的**，所以一次重放不会重复计数。

> [!WARNING]
> `sw.js` 刻意带着那条「保留或丢弃」规则的第二份副本。
> Background Sync 跑在工作线程里，
> 而工作线程是一个经典脚本，无法引入模块。
> 那里的 `queueVerdict` 必须和 `queue.js` 里的 `verdictFor` 保持一致。
> 第 10 阶段那次运行里有两项检查，存在的唯一目的就是抓住这一对漂移。

## 怎么检查它

**`node tests/phase10-test.mjs --only=worker`**
会把入队平台架在 localhost 上，
就注册而言那算是一个安全来源。
它会驱动一个真实浏览器走过安装、预先缓存、离线导航、后备和更新提示。
不需要部署、不需要凭据、不需要网络。

**`node tests/phase14-test.mjs --only=install`** 对本站做同样的事，
之后再用 Playwright 把网络拔掉。

**在推送对任何一个工作线程的改动之前，请先跑其中一个。**
一个会抛出错误的 fetch 处理器，
会让这个来源上的每一个页面对所有已经装了那个工作线程的人失效。
再怎么读那个文件都找不出这一点。
