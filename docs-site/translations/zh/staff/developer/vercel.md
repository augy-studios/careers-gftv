# Vercel

**两个项目，一个代码库。**
每一个都有自己的根目录、自己的环境变量，以及自己的 `vercel.json`。

| 项目 | 根目录 | 域名 | 构建命令 |
|---|---|---|---|
| 入队平台 | `main-site` | `careers.globalfurry.tv` | 无 |
| 说明文件 | `docs-site` | `docs.careers.globalfurry.tv` | `node scripts/build.js` |

两者的框架预设都是 **Other**，安装命令是 `npm install`，Node 20 或更新。
区域是 `sin1`，设定在各自的 `vercel.json` 里，不是在表单里。

**入队平台把它的根目录当静态文件提供**，没有输出目录，也没有构建。
**说明文件网站提供的是 `dist/`。**
它的构建命令和输出目录都在 `vercel.json` 里，
所以一个全新的项目不需要在表单里输入任何东西。

要把一个域名指向某个项目：
在项目设置里加上它，然后在 DNS 服务商那里加上 Vercel 给您的 CNAME。
记录解析成功之后，证书就会签发。

## 决定了整个代码库形状的那个后果

**Vercel 项目从自己的根目录构建，无法伸到外面去。**
所以 `docs-site/api/` 无法从 `main-site/api/_lib/` 引入任何一个文件，
而 5h 的回答是：把两者共用的东西复制一份。

```sh
node gen-docs-lib.js          # write the docs site's copies
node gen-docs-lib.js --check  # fail when one is out of date
```

**对 `main-site/api/_lib/` 或 `main-site/assets/js/` 的改动只是半次改动。**
请运行那个生成器，否则 `--check` 会在部署失败之前先失败。

**生成出来的东西一律不编辑。**
每一份副本开头都会说明这一点，并写明它的来源。
出现在生成目录里的手写文件会让检查失败。
一个没有人声明过的文件，摆在十几个生成文件旁边，
正是下一个人断定整个目录都归他管的原因。

**两个网站真正有差别的地方，都是生成器里的规则**，每一条旁边都写着理由。
它们是登录 cookie、登录状态表、稽核标记、变量列表，以及依赖方那一对。
**一条规则的文本如果不再出现，就会让整次运行停下来**，
绝不会默默丢掉它本来要保住的那个差别。

## 环境变量

每个项目只读取设定在它自己身上的东西，
所以说明文件项目的那四个要在那边重新输入一次。
每一个都记录在它旁边的 `.env.example` 里。

| 变量 | 入队平台 | 说明文件 | 机器人 |
|---|---|---|---|
| `SUPABASE_URL` | 是 | 是 | 是 |
| `SUPABASE_SERVICE_KEY` | 是 | 是 | 是 |
| `SITE_URL` | 是 | 是 | 是 |
| `DOCS_URL` | | 是 | |
| `FORM_WEBHOOK_SECRET` | 是 | | |
| `CRON_SECRET` | 是 | | |
| `TELEGRAM_BOT_USERNAME` | 选填 | | |

> [!WARNING]
> **在说明文件项目上，`SITE_URL` 仍然是入队平台。**
> 它是 WebAuthn 的依赖方标识，
> 把它指向本站会弄坏在入队平台上注册的每一把通行密钥。
> 本站自己的来源是 `DOCS_URL`。

**说明文件项目上 `SITE_URL` 没有设定，是一次本代码库任何检查都看不到的真实故障。**
有两条员工路由整整一个阶段都回应 500，而每一项公开检查都通过，
因为那些检查全都是以陌生人的身份发问的。

**轮换 `FORM_WEBHOOK_SECRET` 需要协调**，因为它存在两个地方：
项目设置，以及每一份表单 Apps Script 的指令码属性。
在这两步之间抵达的提交会被拒绝。
轮换 `CRON_SECRET` 则不需要协调。

## `vercel.json`

**那个文件里任何东西都不能带注释。**
Vercel 会拿一个模式去验证它，
那个模式会拒绝任何它不认识的属性，在根层级和重写规则内部都一样。
一个 `$comment` 键会让构建失败。
理由写在它旁边的 README 里，以及依赖它的那个模块里。

有两个头比其余的都重要，而且两个网站都带着它们：

- **`sw.js` 以 `Cache-Control: no-cache` 提供**，
  并带 `Service-Worker-Allowed: /`。
  一个过期的工作线程会把旧构建无限期地钉住。
- **`build-status.json` 有一个很短的 `s-maxage`**，
  好让一个阶段翻成已上线时能快点传到大家手上。

**说明文件网站的 `includeFiles` 通配符涵盖三个目录**：
两棵内容树和 `api/_generated/`。
公开那棵树之所以被包含进来，是因为导航路由会读取整份页面列表，
好为没有登录的读者也画出一个侧边栏。
找不到它的函数会在第一次请求时抛出错误，并写明是哪一个条目。

**构建在函数被打包之前运行**，正是这一点把 `api/_generated/` 带给了它们。
那个顺序是 Vercel 的，本构建控制不了。

## 让这次构建栽过四次跟头的那条规则

**Vercel 会先比对文件系统，再去查重写规则。**

- 没有 `main-site/robots.txt`，
  因为一个叫那个名字的文件会胜出，那个函数就永远不会运行。
- 没有 `main-site/status/index.html`，理由相同。
- `/admin/:path*` 把一切都送到占位页面，
  而 `/admin` 底下每一个真实页面仍然会胜出。

**而且在一个纯粹的 `api/` 项目里，基于文件的动态路由什么都绑不到。**
`api/content/[...page].js` 在部署上从来没有收到过一个请求，
在本地却看起来完美无缺。
本代码库里的每一条路由都是一个普通函数，用明确的地址寻址。

> [!TIP]
> 一条在本地能作答的路由，不能证明平台会那样路由它。请在部署上检查。
> `node tests/phase13-test.mjs --only=live` 会向说明文件网站的部署
> 问遍一个陌生人能问的一切，而且不需要任何凭据。

## cron

`main-site/api/cron/daily.js`，
由入队平台 `vercel.json` 里的 `crons` 条目排在 UTC 18:00，
也就是新加坡时间凌晨 2 点。
Vercel 会在大约一小时内触发，所以没有任何东西依赖那一分钟。

**它只靠 `Authorization: Bearer $CRON_SECRET` 验证，此外什么都没有**，
因为调用者是一个排程器，没有登录状态。
变量没有设定时，Vercel 什么都不会送。
所以那条路由会拒绝一个不带密钥的请求，而不是假定那是排程器送来的。

它会关闭过了截止日期的职位，
并放弃十四天都没有人回答的申请提示。
它会删除过期记录，并检查每一则已发布职位的表单。
**它绝不会把任何东西下架**，而且跑两次是安全的。

```bash
curl -sS -X POST https://careers.globalfurry.tv/api/cron/daily \
  -H "Authorization: Bearer $CRON_SECRET" | jq
```

**它汇报的地方是管理员概览**，数据来自 `gftvjobs_cron_runs`。
没有人会盯着一个 cron，
所以一次停止触发的运行，否则就是无声无息的。

## 预览部署

**预览部署是另一台主机**，
所以针对生产环境注册的通行密钥在上面不管用。
密码加上验证器验证码仍然可以。
请在有人断定预览部署坏掉之前先说明这一点。

**每一个部署背后都是同一个数据库。**
预览不是沙盒：
在预览上写入示例数据，等于把它放进生产环境的职位板和网站地图里。
