# 工作备忘

**`next-steps.md` 是这次构建据以进行的那份备忘。**
它和规格书一起放在代码库根目录，被 git 忽略，
而且在每一个阶段的开始和结束都会重写一次。

如果您克隆了这个代码库，是找不到它的。那正是这一页存在的原因。
除非被保存下来，否则这个文件会随着最后一次工作会话一起消失。
它是这次构建为什么长成这样的唯一记录。

## 里面有什么

规格书第 0b 节要求四个部分，而这个文件围绕它们长成了八个小节。

| 小节 | 内容 |
|---|---|
| 至今完成的 | 每一个已上线的阶段，浓缩过，附上各自产出了什么。 |
| 本阶段 | 当前阶段，逐部分说明，附上每一部分交付了什么。 |
| 承重的规则 | 那些一旦被破坏就会造成缺陷的东西。 |
| 偏离 | 构建偏离说明书的每一处，编号，并附上理由。 |
| 继续带着走的 | 比它被发现的那个阶段活得更久的未结项目。 |
| 由后续阶段继承的 | 交给尚未开始的阶段的工作。 |
| 已定案的决定 | 以免它们被重新提出。 |
| 未结项目 | 已知，而且不构成阻碍。 |

**偏离记录是最值得先读的部分。**
它们有一百三十多条，都有编号，
每一条都写明说明书说了什么、实际造出来的是什么，以及为什么。
偏离不是错误：它是一个偏离了计划的决定，而它被写了下来，没有被遗忘。

## 为什么它被 git 忽略，却仍然是交付物

**它是一个工作文件，不是产品的一部分**，这正是 0b 说要忽略它的原因。
把它提交上去，等于让一份一天要重写好几次的文件出现在每一次 diff 里，
而且它在两次重写之间就会过时。

**但它是各个阶段实际怎么走过来的记录。**
弄丢它，会让这些代码失去关于自身历史的所有交代。
所以它会在构建结束时，以快照的形式在这里发布。

> [!NOTE]
> 是快照，不是实时文件。承载它的那一页会说明这一点。
> 您在这里读到的是构建结束时那份备忘的样子，
> 而维护者机器上的工作副本在那之后又往前走了。

## 交接是怎么进行的

每一个阶段结束时都会把备忘向前折叠一次，
而这个形状值得知道，因为它正是让这个文件不会无限膨胀的原因。

1. **本阶段** 被浓缩进 **至今完成的**，
   保留后来的读者需要的内容，丢掉工作过程中的笔记。
2. **由后续阶段继承的** 把它的项目交给新的 **本阶段**。
3. 顶部的前言被重写，说明构建目前走到哪里。
4. `build-status.json` 翻转已上线的阶段，
   见[阶段与开发进度](/staff/developer/phases-and-build-status)。
5. 这个阶段让哪些 README 失效，就在同一次改动里更新哪些。

**每一部分单独提交**，提交讯息写明阶段和部分。
备忘会把提交哈希记在它所属的那一部分旁边。
正是这一点，让一年之后有人可以把备忘和 git 日志对着读。

## 在这里阅读它

**整个文件会在这一区块底下重现**，由文件本身生成，
方式和规格书一样。两者都是这个项目自己的文件，没有别的地方持有它们。

> [!WARNING]
> 不要把发布出来的副本当成最新的。请看页面上的日期。
> 如果构建还在进行，代码库根目录的那个文件会比它更新。

**它不是更新日志。**
入队平台上的 `/status` 才是公开的、记录什么时候上线了什么的地方，
而且它是写给使用这个网站的人看的。
备忘是写给即将去改动它的人看的。
