# 7. 申请流程

申请由 Google 表单收集，不在本平台收集。本平台的工作是把住入口、把申请人交接过去，并记录这次交接。然后它记下申请人有没有说自己真的把它做完了。

### 7a. 点击申请

- 只有已登录的申请人才能申请。这是接口上一个服务器端的检查，不只是一个藏起来的按钮。一个未登录的请求要表单地址时回 401，而且不写任何分析记录。
- 一位已登录的申请人点申请时，客户端调用一个需要登录的接口。那个接口：
  1. 验证会话。然后验证这个职位是 `published`、没有超过 `closes_at`（如果设了的话），而且没有被那个全局的申请开关挡住。`closes_at` 为空时这一项通过。
  2. 往 `gftvjobs_analytics` 插一条记录。它带着 `event_type` 为 `apply_click`、职位 id、申请人 id、`did_apply` 为 false，以及 `response_state` 为 pending。
  3. 把 `gftvjobs_applications` 那条追踪记录更新或插入成状态 `started`，并写一条 `gftvjobs_application_events` 记录。
  4. 返回预填好的表单地址，加上它刚刚建的那条分析记录的 id。
- 客户端先开弹窗，然后才开新标签页，顺序照 7c 所定。不要在弹窗出现在屏幕上之前就开那个标签页。
- `closes_at` 一过，申请按钮就禁用，并配一句说明性的文字。状态不是 `published`、或者那个全局开关关着时，也一样。一个没有 `closes_at` 的职位绝不会因为时间而被禁用。
- 依 7f，**一位已经在这个职位上被 `accepted` 的申请人会被永久拒绝**。它和冷却期在同一个地方检查，但它是另一个理由，因为那句话不一样。他们已经拿到那个职位了，而且没有哪一天会改变这件事。绝不要给他们看一个冷却期日期，那读起来像是在邀请他们再试一次。

### 7b. 把申请人的电邮预填进 Google 表单

这件事可行，也值得做。Google 表单支持透过查询参数预填。

- 在 Google 表单里打开那个表单，选“取得预先填入的链接”。在电邮那一栏填一个占位值、提交，然后把生成的链接复制下来。它里面带着那一栏的 `entry.NNNNNNN` 参数。那个数字就是那个字段的 id。
- 把它存进那个职位的 `form_prefill` 映射里。举个例子是 `{"entry.1045781291": "email", "entry.2005620554": "display_name"}`。管理后台的职位编辑器有对应的输入框，并配说明文字解释那些 entry id 是从哪里来的。
- 服务器用表单的基础地址、加上 `?usp=pp_url`、再加上每一对 `entry.NNNNNNN=<值>`，拼出最终的地址。每一个值都做 URL 编码。这要在服务器端从会话拼出来，绝不用客户端送来的值。
- 有两个限制要在管理说明文字里明白写出来。预填的值申请人是可以改的，所以表单回复里的电邮不构成身份证明。而且预填只在 `viewform` 那种地址上有效，`forms.gle` 短链接不行。保存时要校验存下来的地址是一个长格式的 `docs.google.com/forms/.../viewform` 地址。
- 如果一个职位没有 `form_prefill` 映射，就打开那个不带参数的表单地址。绝不要因为没配预填就让交接失败。

### 7c. 交接弹窗

点申请会打开一个弹窗，然后表单才在新标签页里打开。顺序很重要。弹窗必须在焦点移开之前就出现在屏幕上，这样申请人会注意到它升起来，回来时也认得它。是轻轻拍一下肩膀，不是回来时的一次伏击。

**顺序**

1. 点申请。弹窗立刻打开，就在那一次点击的同一个时刻，早于任何网络调用返回。什么都不先等。
2. `api/applications/start` 那个调用并行发出。它返回预填好的表单地址和分析记录的 id。可能的话提前预取那个表单地址，在申请按钮的 `mouseenter` 或 `focus` 时就取。这样到点击的时候它通常已经在内存里，而在点击和新标签页之间什么都不用等。预取还没回来时就退回在点击时去取。
3. 等弹窗真的画出来了，并且从它打开算起至少过了 800 毫秒之后，再打开那个表单。用 `window.open(url, '_blank', 'noopener')`。那一小段延迟是刻意的，好让弹窗在新标签页抢走焦点之前就明显地在屏幕上。
4. 弹窗本身绝不会有被拦截的风险。它是一个页内的 `<dialog>`，和主题弹窗完全一样，而浏览器不管那种东西。弹窗拦截器唯一挡得住的是第 3 步，也就是那个新标签页。把第 3 步保持在那次点击带来的短暂用户激活窗口之内，在 Chrome 和 Firefox 里那是几秒钟。中间不要去等任何慢的东西。
5. Safari 和 iOS 比其他的严。它们可能会拒绝一个发生在 `await` 之后、而不是在点击处理里同步发生的 `window.open`。不要去跟它硬碰。要检测它：如果 `window.open` 返回 null 或者抛错，就当作那个标签页被挡住了。
6. 标签页被挡住时，把弹窗的标题换成“打开申请表单”。显示一个大的主按钮式链接，带着表单地址和 `target="_blank"`。点一个真正的链接是一次全新的用户动作，永远会成功。弹窗其余部分照常运作。另外，不论哪种情况，都在弹窗底部渲染一个安静版本的那个链接。一个标签页有可能开在另一个显示器上，或者开在当前窗口后面，而申请人没有注意到。

**结构**

这个弹窗有三个上下叠着的分区，顺序如下：

1. **标题区。**一开始写着“正在把你带到职位申请表单……”，配一个不确定进度的指示器。申请人回到平台这个标签页时，它换成“告诉我们你的想法”，进度指示器消失。用 `document.visibilitychange` 加上一个 `window` 的 focus 监听来检测回来这件事。再加一道保险：不论如何 8 秒之后就把标题换掉，以防那个标签页从来没有失去过焦点。弹窗被挡住、或者表单开在第二个显示器上时，就会那样。把标题标成 `aria-live="polite"`，好让那次变化被念出来。
2. **给这个职位评分。**五颗黄色的星，默认都是空的。评分是可选的，和申请那个回答互不相干，而弹窗绝不会因为它而卡住。选了就保存，而且弹窗开着的时候可以改。把它做成一组真正的单选框，用视觉上隐藏的 input 和 label，这样用方向键就能操作。绝不要做成一排可点的 span。黄色只用在星星的填色上，所以在浅色和深色两种表面上都要保持可读。旁边配一个把当前值读出来的文字标签，例如“5 分中的 3 分”。
3. **你申请了这个职位吗？**是和否两个按钮，分量相同，两个都不能做成明显的默认选项。“是”会把那条分析记录的 `did_apply` 设为 true、`response_state` 设为已回答、`answer_source` 设为 applicant，`responded_at` 设为当下。然后它把追踪记录移到 `submitted`，并开始 7f 的冷却期。“否”把 `response_state` 设为已回答。它让 `did_apply` 保持 false、追踪记录保持在 `started`，并提供一行让人重新打开那个表单。

**行为**

- 用原生的 `<dialog>` 和 `showModal()` 来做，这样焦点会被锁住，背景也是白拿的。它和这个网站上其他每一个弹窗一样可以关掉。点背景会关、按 Escape 会关，角落里还有一个关闭控件。不要把这个弹窗特殊化成一个比主题选择器还难离开的东西。
- 原生的 `<dialog>` 自己不会因为点背景就关掉，所以要自己加。监听 dialog 元素上的点击，当点击坐标落在内容框之外时就关掉。或者把内容包在一个内层元素里，当点击目标就是那个 dialog 本身时关掉。
- 不回答就关掉是可以的，那会让那条记录保持待回答，而那本来就算作“否”。弹窗会在他们下一次来访时再打开，所以关掉它并不会丢掉什么。
- 回答“是”或“否”会关掉弹窗。它会把页面上那个申请按钮换成相应的状态，要么是冷却期提示，要么是重新打开的链接。已经给出的评分会保存下来，即使之后弹窗在没回答申请那个问题的情况下被关掉。
- **没有回答就是否。**`did_apply` 一开始是 false，并且一直是 false，直到有什么东西正面确认了相反的情况。一条待回答的记录，在所有要紧的地方都当作没有申请。不会开始冷却期，申请按钮仍然可用，漏斗也不会把它算成一次申请。一条没回答的记录和一个明确的“否”之间，唯一的差别是 `response_state` 和 `answer_source` 的值。它们的存在，是为了让分析页面能把一个真正的“否”和沉默区分开。
- 这个提示在人离开之后仍然存在，而它是一种状态，不是一个页面。没有 `/survey/` 这条路由，它根本没有自己的任何路由。见下面的“续答一个待回答的提示”。
- 再问一次是为了把一个可能的“是”捞回来，不是为了扣住什么，所以本平台没有任何东西是以回答为前提的。

**续答一个待回答的提示**

- 服务器是事实来源。`GET api/applications/pending` 返回这位申请人 `response_state` 为待回答的那些 `gftvjobs_analytics` 记录。每一条带着它的记录 id、职位 id 和职位名称。它从会话 cookie 读出申请人是谁，绝不从调用方那里拿一个 id。
- 平台每一个页面上都跑着一个小的共用脚本。如果存在一个申请人会话，它就在每次页面加载时调用那个接口一次，有东西回来就打开弹窗。它直接进到“告诉我们你的想法”那个状态，没有跳转那一步，也没有进度指示器。这个弹窗是一个接收一个记录 id 和一个职位 id 的组件，所以它可以挂在任何页面上。
- `localStorage` 也存着同一个记录 id，纯粹作为一条快路。这样弹窗可以在那次请求返回之前就出现，就在申请人刚离开的那个职位页上。把它当作一份可能是错的缓存。如果服务器说没有待回答的，就把它清掉，什么都不显示。这也正是为什么那个服务器端检查非有不可：换一台设备或者清掉浏览器数据，否则就会丢掉这个提示。
- `/account/tasks` 上那条待办会就地打开同一个弹窗。如果它需要能被链接到，就在职位上用一个查询参数：`/jobs/{uuid}?prompt={analytics_row_id}`，绝不用一段嵌套的路径。这个提示不是一个自己的资源，绝不该被搜索引擎收录，也不配拥有一段网址。打开任何东西之前，先校验那条记录属于会话里的那位申请人。弹窗一打开就用 `history.replaceState` 把那个参数去掉，免得它留在一个被分享出去的链接里。
- 任何时候都只显示一个弹窗。如果有好几个提示待回答，就取最近的那一个，其余的留给以后的页面加载。
- 一个职位上还有回答待回答的时候，那个职位上的申请按钮会被替换掉。取而代之的是一句“你有一个关于这次申请的问题还没回答”的提示，点了会重新打开弹窗。这样第二次交接就不会叠在一个还没解决的上面。
- 每日定时任务会把超过 14 天仍待回答的分析记录改成 `response_state` 为 `no_response`。`did_apply` 保持 false，`answer_source` 设为 `timeout`。到那时候，申请人的任何权限都不会改变，因为沉默本来就已经被读作“否”了。这个超时的存在，是为了让弹窗不要永远地再冒出来，也为了把那条记录在报表上结掉。
- 这个弹窗在手机上必须好用。满宽的弹层、拇指够得到的按钮、大到能准确点中的星星，而且不依赖悬停。

### 7d. 关于不让标签页关掉这件事

我要求过在关掉标签页之前强迫用户先回答。那不是浏览器会允许的事，所以就做那个最接近、又诚实的版本，不要浪费力气去跟它对抗：

- `beforeunload` 是唯一可用的钩子，而它能做的只是弹出一个浏览器自己生成的确认框，文字网站控制不了。Chrome、Firefox 和 Safari 都会忽略自定义的信息。申请人每一次仍然可以确认然后离开。而且它只有在他们先和页面互动过之后才会触发。
- 只在弹窗真的开着而且还没回答的时候注册 `beforeunload` 处理。任何一种关闭都要把它移除，不论那是“是”、“否”、Escape、背景，还是关闭控件。弹窗被关掉之后不要让它继续挂着，因为申请人已经告诉你他们暂时不想处理它了。这样就能给出一个真正的“你确定要离开吗”提示，而不必假装那是一把锁。
- 不要去尝试任何那些不友善的绕法：不要反复 `alert()`、不要用 `history.pushState` 做后退键陷阱、不要锁全屏、不要用 `unload` 猛发信标。浏览器会挡掉或者限制这些做法，它们会让网站被标记，而且它们是在为一个不属于申请人的数据质量问题惩罚申请人。
- 真正的安全网是 7c 那个一直在的弹窗，它会在下一次来访时重新打开。它绝不当场要一个回答。
- 让这个回答变可靠的，是第 13 节那个 Google Apps Script 回调，它独立于申请人点了什么去确认提交。那个也要做。弹窗照样保留，因为它涵盖那些没装脚本的表单，而且它同时也在收评分。

### 7e. 撤回

- 申请人可以撤回，那会把追踪状态设为 `withdrawn` 并写一条事件记录。在屏幕上讲清楚，在这里撤回并不会删掉他们的 Google 表单回复。要说明如果需要把它删掉，请联系团队。
- 撤回会把 7f 描述的重新申请冷却期清掉，这样一个中途退出的人，不会因为改变主意就被锁在那个职位外面。

### 7f. 重新申请的冷却期

一位申请人申请过一个职位之后，三个月内不能再申请同一个职位。

- 冷却期只在得到一次正面确认时才开始，哪一个先来算哪一个。那要么是申请人在 7c 的弹窗里点了“是”，要么是第 13 节那个回调报告了这次提交。
- 点“否”什么都不会开始，不理会那个弹窗也一样。一个没回答的提示读作“否”。一位没回答就把标签页关掉的申请人，对申请按钮仍然拥有完整的权限。绝不要单凭那一次点击就推断出一次申请。
- 确认之后，在 `gftvjobs_applications` 那一行上设 `applied_at`，并把 `cooldown_until` 设成三个月之后。把日期存下来，而不是在读的时候算。这样以后政策变了，这条规则仍然稳定，而管理员也可以针对单独一行做覆盖。
- 在申请接口里于服务器端强制执行，不要只靠把按钮藏起来。一个仍在冷却期内的职位的请求，会返回一个清楚的错误，而且不写任何分析记录。
- 一个在冷却期内的职位，它的申请按钮被替换成一个禁用状态。上面写着“已于 3 月 4 日申请。你可以从 6 月 4 日起再次申请。”在搜索结果的卡片上也显示同一句。这样就不会有人点进去才被挡回来。
- 冷却期是按申请人也按职位的。另一个职位不受影响。一个关掉之后又重新贴出来的职位会拿到一个新的 uuid，所以它是一个新的职位，没有冷却期。在管理说明文字里提一下这件事，因为对真正重新开放的职位来说，那就是那条预留的出口。
- 管理员可以在申请人追踪页面上，对单独一行豁免冷却期。那会清掉 `cooldown_until`，并写一条事件记录写明是谁做的。
- **状态变更绝不碰冷却期。**一位职位发布者把某人在流程里移来移去时，`applied_at` 和 `cooldown_until` 原封不动。`accepted` 是这样，`rejected` 是这样，其他每一个状态也是这样。申请人把本来就在服的那段期间服完。只有三件事会写那两列。一次确认过的申请会设它们，依 7e 一次撤回会清掉它们，而依上面那一条，一次明确的豁免会清掉 `cooldown_until`。婉拒不是豁免。把它做成豁免，会让人在被回绝的当天下午就重新申请，那对谁都没好处。
- **冷却期一跑完，一位被婉拒的申请人可以再次申请**，而追踪记录会重新从 `started` 开始。这道门的全部就是那个冷却期。婉拒不是封禁，而那些事件历史保留着到底发生过什么的记录。所以 `rejected` 和 `started`、`withdrawn` 一样，都属于一次新的申请可以重置的状态。那份清单在 `api/_lib/apply.js` 里。
- **一位被录取的申请人不能再申请那个职位**，不论有没有冷却期。他们已经拿到那个职位了。申请控件会明白这样写，而且绝不显示一个日期。一个日期是在邀请人回来，为一样他们已经拥有的东西再试一次。这是 7a 里唯一一个和时间流逝无关的拒绝。

### 7g. 申请人面板

账户区在个人资料之外还有两个列表页面。两个都是私密的，也都需要一个申请人会话。两个都必须在职位已经关闭、过期或归档的情况下仍然能用。

**我的申请（`/account/applications`）**

- 申请人申请过、或者开始申请过的每一个职位，最新的在前。每一条显示状态、他们申请的日期，以及有冷却期在生效时的冷却期状态。
- 和管理端一样的分组标签页，这样他们可以筛选出已提交的、进行中的，或者已经结掉的。
- 每一行都链回那个职位在 `/jobs/{uuid}` 的地址。那个链接即使职位后来关闭、过期或者被归档了，也必须打得开。这样申请人永远可以重读一遍自己当初申请的是什么。
- 7c 里任何没回答的提示，也会出现在下面那个待办事项页面上，那里才是它的正式归处。
- 依 7e，有撤回操作。
- 空状态指向 `/search`。

**收藏的职位（`/account/saved`）**

- 一样的处理。申请人收藏过的职位，包括后来已经关闭或过期的。那些仍然留着显示，配一个清楚的“已不再接受申请”标记，绝不从列表里消失。
- 有取消收藏的操作，而 `/search` 里的职位卡片和职位详情页上也都有一个收藏／取消收藏的开关。
- 收藏需要一个会话。对未登录的访客，收藏控件会打开和申请一样的那个登录提示，也就是第 4 节写的那个。他们回来之后就把收藏完成。
- 按最近收藏排序，并配一个“仍开放”对“已关闭”的筛选。

**待办事项（`/account/tasks`）**

一个统一的收件箱，装着任何本平台需要申请人处理的事。它的存在，是为了让管理员的一个请求有地方落脚，既然通知现在只在平台内。

- 有两个来源汇进这份列表，而这个页面在读的时候把它们合起来：
  1. 没回答的申请提示，从 `response_state` 为待回答的 `gftvjobs_analytics` 记录实时推导出来。不要把它们复制进事项表。那条分析记录仍然是唯一的事实来源，而复制一份就保证了两者迟早不一致。
  2. `gftvjobs_tasks` 里的记录，那是管理员发起的事项所在的地方。
- 一开始要支持两种事项类型。`info_request` 是管理员在推进一份申请之前需要更多细节的情况。`notice` 是一条单向的消息，没有东西要提交。类型那一列要留着开放，这样以后加更多类型不用迁移。
- 每一条显示一个标题、有关联的话显示相关的职位、是谁发起的、什么时候，以及它的状态。未结的排在前面，最新的在前。已处理的收进一个“最近完成”的分区，绝不消失。
- 打开一条申请提示，会就地打开 7c 那个弹窗。打开一条索取资料的事项，会展开一个内嵌面板，里面是管理员的信息和它带着的那些问题。
- 目前把回复保持在一个来回。管理员问、申请人回一次、管理员读完把这个事项结掉。这刻意不是一条会话串。没有一个“好好去做那件事”的决定，它不该长成那样。

*事项上的问题*

一个 `info_request` 可以带一套问题，而不是只有一个自由文本框。职位发布者在 8.3 里编写它们，申请人在一次提交里回答全部，那仍然是一个来回。

**有两个问题是内建的，绝不属于发布者那一套。**它们是“你申请了这个职位吗”和那个职位评分，两个都来自 7c。它们属于那个申请提示，而且它们是从 `gftvjobs_analytics` 推导出来的，绝不作为问题存储。任何编写器都不能编辑、调整顺序或者移除它们。发布者的问题也绝不会出现在交接弹窗里面，理由 7c 已经给过。那个弹窗是轻轻拍一下肩膀，不是一次伏击。在它上面挂一份必填的表单，会让关掉它变成有代价的事。

**一套问题发给谁，是在发出去的时候决定的**，而且正好只有两个选择：

- **选中的申请。**发布者在追踪页面上勾一份或多份已有的申请。每一份各自拿到自己的一个事项。
- **这个职位，从现在起。**这套问题存在职位上。从那时起每一个申请的人，都会在被交接的那一刻自动被发起一个事项。已有的申请人不受影响，除非发布者也发给他们。**这是一份问每一个申请者的表单，而第 10 节第 1 项已经修订过来允许它。扩展这一块之前先读那一项。**

一位发布者发给不止一个人时，会在写下任何东西之前，完整看到到底谁会收到。那和 8.5 用在批量邀请上的是同一条规则。每一位接收者拿到一个独立的事项，各自带着那套问题自己冻结的一份副本。所以处理其中一个，或者一套发错了，都是按申请人各自算的，绝不是一行共用的记录。

这套问题本身：

- **四种题型，没有一个决定就不会再多。****简答**是一行，**长答**是一段。**单选**从一份清单里正好挑一个，**多选**从一份清单里挑任意个，包括一个都不挑。一个是或否的确认，就是一个只有一个选项的多选题。
- 每一题带一个稳定的 id、一个类型、一个题目、它是不是必答的，以及两种列表类型还要带它按显示顺序排好的选项。
- 依 3a，**问题要用每一种已上线的语言写，并以读者自己那种语言显示**。编写器提供一种语言一个标签页，和职位编辑器完全一样。不像一条发给某一个具名对象的消息，一套问题现在可以发到每一个申请的人，而他们的语言各不相同。**某一种语言留空时，退回用一个已经写了的。**那是这个网站上其他每一条字符串都遵循的同一条规则，而且它绝不会渲染成空的。
- **一个选项存下来的值是与语言无关的。**题目是分语言的，值不是。一个答案记的是那个值，所以同一个答案在两种语言下都渲染得出来，而校验也不取决于申请人当时在读哪一种语言。把翻译过的题目当作答案存下来，会让一位华文读者的答案在英文下读不懂，也没办法和选项对上。
- **自由文本框永远和问题一起提供，而且关不掉。**一个被问了三件具体事情的人，常常需要说第四件。一份没有办法说“这几个都不太对”的表单，收到的答案比有这个办法的差。
- **答案在服务器端对着存在那个事项上的问题集校验**，绝不对着浏览器送回来的东西校验。每一个必答题都必须有答案。一个单选或多选的答案，必须是那一题自己的选项值之一。一个指向该事项没有的问题的答案会被拒绝，绝不存下来。
- **一套问题一发出去就冻结了。**问题可以在编写器里自由地新增、编辑、调整顺序和删除，之后完全不行。改一套已经发出去的问题，会让已经给出的答案变成孤儿，也会改掉已经被读过的那些答案的意思。搞错了就发起一个新的事项、把旧的结掉，那是看得见的，而且是正确的代价。改存在一个职位上的那一套，只会改变以后的申请人被问到什么，绝不碰一个已经发起的事项。
- **给这套问题设上限，而且要设得低。**二十题，每题的选项数量和每个答案的长度也都有上限。
- **任何形式的文件上传都不行。**问题上不行、自由文本框上不行、永远不行。任何需要文件的东西，都透过那个职位的 Google 表单去要，或者用其他途径安排。
- 申请人提交之后看得到自己的答案，就和他们现在看得到一次普通回复一样。一个他们被问到、但不必回答的问题，显示为未回答，绝不显示成空白。
- 账户导航上一个徽章显示两个来源加起来的未结数量。这样这个页面不用电邮、也不用推送通知就找得到。
- 深层链接：`/account/tasks?task={task_id}` 打开某一条特定的事项，而申请提示保留 7c 那个 `/jobs/{uuid}?prompt={analytics_row_id}` 的形式。两种情况都要对着会话校验归属，并在处理完之后用 `history.replaceState` 把那个参数去掉。
- 空状态要读起来像是一件好事，不像一个错误。

**账户设置（`/account/settings`）**

个人资料字段、修改密码、Telegram 关联，以及底部一个明确分隔开的危险操作区。

*危险操作区*

涵盖删除账户、解除 Telegram 关联、关掉 Telegram 两步验证，以及以后加进来的任何其他破坏性操作。每一个都走同样的三步，顺序固定，而且没办法跳过：

1. **后果。**点那个操作会打开一个面板，把到底会发生什么、以及什么是撤销不了的写清楚。取消至少和继续一样显眼。对删除账户，要明白说出已经提交的 Google 表单回复是由 Google 保管的，这个操作并不会删掉它们。要说明那些要另外联系团队。
2. **打字确认。**他们要打自己的用户名才能继续。不是一个勾选框、不是打 “DELETE”，是他们的用户名，这样这个操作没办法靠肌肉记忆完成。比对时区分大小写，只去掉首尾空白。
3. **密码。**他们输入自己当前的账户密码，由一个专门的接口在服务器端对着 bcrypt 哈希验证。绝不接受一个来自客户端的“密码是对的”信号。如果那个账户开着 Telegram 两步验证，这一步还要一个来自机器人的新验证码。那正是有它的意义。

然后那个操作才执行。另外还有几项要求：

- 对这些接口做严格限流，并在几次密码尝试失败之后把危险操作区锁一个小时。
- 每一个破坏性操作在执行之前都写一条审计记录，这样那条记录能在删除之后留存下来。
- 删除一个账户会级联删掉申请人自己的那些记录。它会保留 `gftvjobs_analytics` 记录，把 `applicant_id` 设为空，这样历史的漏斗数字仍然完整。它会立刻让那个账户的每一个会话失效。
- 事后显示一个最终的确认画面，不要只是跳回首页。

*救援码*

- 两个面板，一套一个，各自显示还剩几个码、是什么时候生成的，以及查看剩余数量和重新生成的按钮。生成之后绝不再显示一个码。
- 账户救援那个面板带着这个页面上最强的一则警告。系统里没有电邮，所以这些码是不求管理员就能回来的唯一途径。
- 依 5c，生成任何一套都需要当前密码。

*受信任设备*

- 依 5d，列出受信任设备，写上每一台是什么时候加的、上次什么时候用的，另有每台一个撤销和一个全部撤销。
- 在列表里标出当前这一台，免得有人没意识到就把自己正坐着的这一台撤销了。

*Telegram 两步验证*

- 一个“关联 Telegram 做两步验证”的控件，会生成一个短时有效、只能用一次的关联令牌。它显示一个 `t.me/careersgftv_bot?start=<token>` 的深层链接和同一个链接的二维码。它还以文字显示那个令牌，给想要复制粘贴的人用。
- 关联好之后，显示所关联的 Telegram 显示名称和关联的日期。再加上发一条测试消息、解除关联，以及切换登录时要不要两步验证这几个控件。
- 两步验证开着时，登录流程在密码之后多一步。平台在 Telegram 上给申请人发一个六位数验证码，浏览器提示他们输入。如果推送没到，申请人也可以自己从机器人那里要一个验证码。
- 验证码是六位数、五分钟内有效、只能用一次、以哈希存储，并在一次成功登录或者发出一个更新的验证码时作废。对每个码和每个账户都设尝试次数上限。在这一步，一个来自 `gftvjobs_2fa_backup_codes` 的码可以代替一个 Telegram 验证码。
- 如果申请人没办法再用 Telegram，5c 里他们的两步验证备用码就是回来的路。要求那一套码在两步验证能被打开之前就存在，没有的话就在同一个流程里生成。明白说出，Telegram 和那些码都丢了就得去找管理员。

**旧职位的可见性规则**

修订第 4 节那条 404 规则。下面任何一种情况成立时，一个职位在它 uuid 的地址上是打得开的。它是 `published`。它是 `closed`。或者请求者是一位对它有 `gftvjobs_applications` 记录或 `gftvjobs_saved_jobs` 记录的申请人。一个 `draft` 职位只有正在预览它的管理员看得到。其他一切都是 404。一位申请人有过往记录的已归档职位，会以只读状态渲染，并配一句说明那个职位已经不再有效。

### 7h. 反馈一个翻译问题

国际兽视这一边未必有人两种语言都读得够好，能抢在申请人之前发现一个翻坏的职位。所以申请人就是那个纠错回路。在有人说之前，就假定每一份翻译都是错的，并且让“说出来”这件事很容易。

- 每个职位上一个安静的控件，写着类似“反馈翻译问题”。不是横幅、不是提示，也绝不是一个自己冒出来的弹窗。它就在职位的下方，和分享与返回那些链接摆在一起。
- 同样的控件也出现在其他任何大段显示翻译内容的地方，以及界面本身上。一位在导航里看到一个翻坏的标签的读者，应该能够把它反馈出来。他们不该需要先搞清楚那是一条界面文字、而不是职位的一部分。那个反馈表单问的是哪里不对，不是那是哪一类东西。
- 打开它会显示四样东西。哪一种语言的版本有问题，默认是当前正在读的那一种。哪一部分，默认是整个职位。一个写哪里不对的框。以及一个可选的、写更好写法的框。
- **一个建议的写法绝不会被自动套用。**每一次都有一位管理员先读过。在表单上把这件事说出来，这样反馈的人知道会发生什么，也不会以为自己写的文字已经上线了。
- 反馈的人可以用任何一种语言写。不要逼他们用自己正在反馈的那一种语言，因为那往往是他们读得最差的一种。
- 反馈需要一个申请人会话，这样团队才能回过头来找他们。对未登录的访客，依第 4 节，这个控件会打开和申请一样的那个登录提示，并在回来之后把反馈完成。
- 和其他每一次写入一样，按账户和按 IP 限流。
- 提交时明白确认一声，并说会有一个人来看。不要承诺时间。
- 反馈存在 `gftvjobs_translation_reports` 里。它们不是事项。它们是从申请人那边发出去的，而不是本平台需要他们做的事。所以它们不属于 `/account/tasks`，也绝不能加进它那个徽章数量里。需要追问的管理员，就发起一个普通的 `info_request` 事项，那张表本来就是干这个的。

### 7i. 翻译帮手

第 7h 节让任何申请人都能反馈一份翻译读起来不对。这里是另外一半：一个给那些真的能修的人的长期角色。

国际兽视这一边未必有人把平台出版的每一种语言都读得懂。把翻译审阅当成上线之前拜托一次的人情，就等于保证第二个职位会比第一个更糟。所以它改成一种能力。

**他们是谁**

- 一位翻译帮手是一个普通的 `gftvjobs_users` 账户，由管理员为某一种语言授予这个角色。他们是会说那种语言的人，不是员工。他们刻意不走 `gftvhello`，也不走那一层管理权限。最适合来修华文的那个人，没有理由是国际兽视的员工。
- 授予是按语言的，记在 `gftvjobs_translation_helpers` 里。一旦有了第三种语言，一个读华文的人就不该去批淡米尔文，而一个单独的布尔值会让他能这么做。
- 授予时要填一个理由，记在那一行上，这样一年之后来看这份名单的管理员，会知道每一个人为什么在上面。

**他们能做什么**

- 自由地编辑他们那种语言的任何一份翻译，不需要审批。
- **他们不能把一份翻译变成上线的。**只有员工能设 `is_ready`，而那正是读者所依赖的那个标志。所以权限可以在信任之前就给出去，而一位帮手也不会不小心把一个做了一半的职位发出去。**是员工，而不只是管理员**，2026 年 9 月 4 日在第 14 阶段第 6 部分修订。这个勾对任何员工账户开放。一位设不了它的职位发布者，就没办法用两种语言发布自己的职位。这一条对一位帮手所做的承诺是：在读者读到之前，会有人先读过他们的草稿，而不论怎样那个承诺都是守住的。偏差 131。
- 看得到还缺什么：他们那种语言里每一个没有翻译的职位、部门和标签，以及每一份开了头但还没可发布的翻译。这和 8.11 是同一个清点视图，范围收在他们那种语言，并且没有管理端那些操作。

**就地提出一个修改建议**

帮手专区不是唯一的入口。一位帮手在读任何一页时，都可以选中读起来不对的那段字，并就地为那一整段提出一个替换。他们完全不用离开页面，也完全不用知道什么是词典的键。

- 在一个可翻译的区域里选中文字，会出现一个小控件让人提出修改。这个网站上所有可翻译的东西，本来就带着一个说明它出处的属性。界面文字渲染在带 `data-i18n="key"` 的元素里，而内容渲染在标着它的表、行和字段的元素里。标注图层从选区往上走去找到它，所以帮手从来不用打任何标识符。
- 这个建议以 `origin` 为 `annotation` 存进 `gftvjobs_translation_reports`，和 7h 那些普通反馈放在一起。**一个队列，不是两个。**不论一条是从表单来的还是从选区来的，管理员都在同一份列表里处理。
- 锚定沿用 W3C Web Annotation Data Model 的 `TextQuoteSelector`。存下确切的那段引文，外加两边各一小段文字。那值得照抄，而不是自己发明。一个建议在周围的文字被改过之后仍然找得到。找不到的时候，它会显示成已脱离，绝不会被悄悄套用到错的地方。
- 针对界面文字的建议是一次代码改动。那些文字在 `assets/i18n` 里，正是这一点让这个网站不用构建步骤，也让那些词典能为离线预缓存。所以管理视图显示那个键、当前的写法，以及那个建议。由一位开发者去套用它并部署。在管理视图里把这件事说清楚，而不是让一位管理员点了批准之后纳闷为什么什么都没变。**不要做一个界面文字编辑器**，也不要为了省掉那次部署就把词典搬进数据库。
- 针对内容的建议，也就是一个职位、部门或标签，管理员可以直接套用，因为那些文字在数据库里。

**这个图层本身**

- 默认是关掉的，从账户菜单里切换。一位帮手首先是一位读者，而选中文字这件事必须照常能用来复制。
- 只有被授权的帮手和管理员看得见。对其他所有人，那些属性只是没有作用的标记，而这个图层根本不会加载。
- 已经存在的建议，会在被标注的那一段上显示成一条淡淡的下划线，配一个数字。正是这一点，把它从一个意见箱变成了一次审阅。一位帮手看得到什么已经被提过，于是不会再提一次。
- 依第 3 节，**在任何宽度下都要优雅**。在宽屏上，建议在文字旁边一个面板里打开，被标注的那些段落和它对齐。1024px 以下它是一个底部弹层，和 `/search` 的筛选以及交接弹窗遵循同一种做法。选中的内容仍然显示在它上方。触屏上的选取并不精确，所以那个弹层会显示捕捉到的那段引文，并让人按词去调整，而不是要求一次完美的拖动。
- 从头到尾都能用键盘到达。一位没办法用指针的帮手，用键盘选取并打开同一个控件，而被标注的那些段落按阅读顺序可以获得焦点。

**这并不取代什么**
