# 0c. 公开发布

每一个阶段做完就推上 GitHub 并部署到生产环境。从第 3 阶段起网站就是活的、能用的，而后面的阶段还没做。所以界面必须老实说清楚哪些东西还不在。

### 边做边上线的规矩

- `main` 永远是可部署的。一个阶段是以一个做好了才合并的分支落地，绝不是 `main` 上一个做到一半的提交。
- 第 1 阶段那整套迁移在第一天就跑完，所以数据库跑在界面前面。那是刻意的。这意味着一个在后面阶段才打开的功能，不需要新的 SQL。
- 绝不要上线一个去调用还不存在的接口的控件。还没做的功能以下面说的禁用状态显示，而它的点击处理只做一件事：解释。

### 构建状态的唯一来源

- 一个文件，`main-site/assets/build-status.json`，装着阶段列表。每一条带一个编号、一个短名称、一个 `shipped`、`building` 或 `planned` 的状态，以及一段平实的说明。旁边还有一张功能键对应阶段编号的表，例如 `saved_jobs: 6`、`telegram_2fa: 11`、`offline: 10`。
- 其他一切都从那个文件读。一个阶段上线时唯一要改的就是把它翻成 `shipped`，而且任何地方的文案都不会把阶段编号写死。
- Telegram 机器人和说明文件网站读的是同一个文件，所以三边保持一致。

### 它长什么样

- **全站提示条。**顶部一条窄窄的、可关掉的横幅，写着国际兽视入队平台正在分阶段开发和发布，并附一个通往状态页的链接。关掉的状态记在本地，一个阶段上线时重置。保持它安静，一行，不要用颜色喊。
- **禁用的控件。**任何一个还没上线的功能所对应的控件，都保持可见并禁用，绝不隐藏。原因就写在它上面：“将于第 5 阶段推出。造成不便，敬请见谅。”就用这个措辞，阶段编号从功能表里取。把它藏起来，是在教人这个功能不存在；把它显示成禁用的，才是告诉他们它就要来了。

### 维护开关

一个控件可以被禁用的第二个原因，2026 年 8 月 21 日加的，依 8.12 在第 7 阶段做出来。一个已经上线的功能可能会坏，或者在修某样东西时需要先下架。在此之前，唯一的手段是重新部署。

- **管理员可以把任何已上线的功能临时关掉。**再用同样的方式打开。这不是阶段变更，而且它绝不改动 `build-status.json`。那个文件是“做了什么”的记录，而一个覆盖开关是“现在什么是好的”的记录。把两者混在一起，会让一次部署悄悄撤销一次故障处理。
- **覆盖开关放在数据库里**，在 `gftvjobs_settings` 里，因为管理员没办法从后台去改代码库里的一个文件。阶段列表仍然是那三方都读的一个静态文件；覆盖开关和它并排读出来，在用到的地方合并。
- **“关”就是关，接口也一样。**每一条挡在被关掉的功能后面的路由，都以同一句话回 503。一个禁用的按钮拦不住任何一个手上有接口地址、有一个旧标签页，或者有第 10 阶段排队离线操作的人。而如果一个功能是因为坏了才关的，那接口正是坏掉的那个东西。
- **它有自己的一句话，不是阶段那一句。**“我们正在修复，暂时无法使用”，再加上管理员写的备注，那是可选的，并按原样显示给公众。跟一个上星期还在用这个功能的人说它“将于第 6 阶段推出”，是在对一个已经上线的功能说谎。那也让一次真正的故障和一个还没做的功能变得分不出来。
- **有些功能永远不能被关掉。**它们放在代码里一份固定的禁止清单上，绝不做成一个设置。那涵盖两套账户体系的登录和注册，以及维护页面自己所依赖的一切。把登录关掉，会把每一个申请人锁在外面而无路可回，还可能把管理员锁在那个本来可以撤销它的页面外面。那个页面把这些开关显示成永久不可用并说明原因，而不是把它们藏起来。
- **状态页会说出来。**一个被关掉的功能会出现在 `/status` 上，标为当前不可用，并带上它的备注。那个页面本来就是别人想知道发生了什么事时会去的地方。
- **还没做的路由。**属于后面阶段的路由，在正常布局里渲染一个占位页面。它带着同一句话、一行关于那个阶段涵盖什么的说明，以及通往状态页和 `/search` 的链接。绝不是 404、绝不是一个空白页，并且要把它们标为 `noindex`。
- **`/status` 状态页。**公开的，从页脚和提示条链过去。它列出每一个阶段的状态和说明、标出当前那一个，并明说不承诺任何日期。它同时也是变更日志：一个阶段上线时，它那一条会多出一行，写有什么变得可用了。
- **管理后台。**一样处理。一位员工点进一个还没做的分区，得到的是同一句话，而不是一个空画面。
- **Telegram 机器人。**一个所依赖的功能还没上线的指令，回的是同一句话，而不是失败或者干脆不吭声。
- **说明文件网站。**任何一个描述还没上线的功能的页面，顶上带一个提示框，写着同一句话。这样说明文件可以走在开发前面写，而不会误导任何人。

### 撤掉它

当每一个阶段都是 `shipped` 时，把提示条和占位路由的处理拿掉。`build-status.json` 留着，因为同一套机制对之后要做的事还有用，并把上面那些上线说明留着当变更日志。

**`/status` 是被改作他用，而不是撤掉**，它是构建状态机制里唯一一个比整个开发过程活得更久的部分。一旦没有什么是还没做的，这个页面所回答的问题就变了。它从“什么还没到”变成“它现在有没有在正常运行”。那才是别人真正带着来到一个状态页的问题。2026 年 8 月 26 日加的，完整规格写在下面。

### 开发结束之后的服务状态页

以 Atlassian 的状态页读起来的样子为蓝本：一句总述、一份组件清单、可用率历史，以及过往的事件。公开的、不需要登录，仍然从页脚链过去。

**其余一切都遵循的那一条规矩：这个页面绝不宣称自己知道得比实际多。**一个因为什么都连不上、于是说“一切系统正常”的状态页，比没有这个页面还糟。那正是这一节要防的那种失败方式。下面每一个面板都分三种状态，不是两种：正常、不正常，以及没有答案。

#### 四个面板

1. **总述。**一句话和一个颜色：一切正常、有东西降级，或者有东西挂了。它是推导出来的，绝不是手打的，这样它不可能和它下面那些面板互相矛盾。

2. **组件，实时。**功能表里每一个可切换的功能，取自维护开关所写的同一份 `feature_overrides`，透过已有的 `api/public/feature-status`。一个被关掉的功能显示为不可用并带上管理员的备注，和开发期间完全一样。禁止清单上那些功能也列出来，而且永远显示为可用。它们没办法被关掉，而把它们略去会让这份清单看起来比整个网站短。

3. **可用率，九十天。**每个组件一条横条，一天一格，取自真正的探测数据，而不是取自平台对自己的任何说法。见下面的探测。

4. **事件。**两个来源，标示方式不同，因为它们是两种不同的主张：
   - **已声明的。**管理员把一个功能关掉又打开。开始、结束、备注和时长，全都可以从已经存在的 `FEATURE_DISABLED` 和 `FEATURE_ENABLED` 审计记录推导出来。8.12 之所以两个方向都记，正是为了这个：一次没人记下结束时间的故障，就是一次没人量得出来的故障。
   - **观察到的。**探测程序连不上某样东西，而没有任何人声明什么。这些才是真正值得有的，因为它们是没人醒着的时候发生的故障。

#### 探测程序，以及它为什么不放在 Vercel 上

**一个托管在它所监控的东西上面的状态页，在它本来就是为之而存在的那次故障里毫无用处。**这正是 Statuspage 之所以是一个独立服务的全部原因，而这不是靠小心就能解决的问题。

所以探测程序跑在那台已经托管着 Telegram 机器人的 Debian VPS 上，依第 15 节。那台机器是整个架构里唯一一个真正在 Vercel 之外的组件。它已经在持续运行，它已经拿着 `SUPABASE_URL` 和 `SUPABASE_SERVICE_KEY`，而且它已经在这个代码库里了。它是一个已经存在的进程里的一个循环，而不是一个新的服务。

- **每六十秒**请求一小组固定的公开接口。记下每一个的状态码和响应时间：`/api/public/feature-status`、`/search`、一个种子职位页面，以及 `/api/public/jobs.json`。四个都是公开且只读的，所以探测程序绝不往平台写任何东西，也绝不需要平台的任何凭据。
- **写入 `gftvjobs_status_days` 和 `gftvjobs_status_incidents`**，那是两张新表。用 service key 从 VPS 直接写，透过那个拥有它们的函数。不经过平台上的任何接口，因为恰恰在最要紧的那种情况下，平台上的接口是不可达的。
- **保留九十天。**第 11 节的每日定时任务会把更旧的清掉，和它删的其他东西一起。
- **一个连不上 Supabase 的探测程序什么都不写，也什么都不说。**它不会积压重试，也不在本地缓冲。数据里的一个空档就是一个诚实的空档，而页面把它画成“没有数据”，绝不画成任何一种状态。
- **机器人不是那个监控。**它不会为一次失败的探测给任何人发消息。告警是另一个决定，后面还挂着一套 on-call 的安排，而那不在这里的范围内。这里换来的是一个别人可以自己去看的页面，而那正是当初要的。

#### 这个页面绝不能做的事

- **绝不显示一个它没有测量过的绿色日子。**一个没有探测数据的日子画成未知，用一个中性的颜色，并在图例里说明那个状态。
- **绝不在一段有空档的时期上算出一个总的可用率百分比**，除非同时说明覆盖率是多少。用 60 天的数据算出“90 天内 99.9%”，是一个带着小数点的编造。
- **绝不在这个页面上报告说明文件网站或者 Telegram 机器人的状态**，除非它们也被探测。一份清单悄悄地只涵盖了平台，看起来却像涵盖了整个项目，那是同一个谎的另一种形状。
- **让它在没有 JavaScript、没有会话的情况下也读得了**，并在边缘节点上短暂缓存。它是别人在出事时会去加载的那个页面，所以它应该是全站最便宜的页面。

#### 什么时候做

探测程序、那张表和重做过的页面属于**第 12 阶段**。它们和其他那些要等整个开发结束才有意义的东西放在一起。切换本身就是把阶段列表从页面上拿掉。它以每一个阶段都是 `shipped` 为前提，这样两半可以先做好再交接过去，绝不用赶。

在那之前 `/status` 继续做它现在的工作。两者绝不能同时出现。一个既列着什么还没做、又列着什么正在出问题的页面，会给读者两个不同的“这东西可能用不了”的理由。它不给读者任何办法分辨自己看到的是哪一个。那和维护开关之所以要有自己一句话，是同一种混淆。

**提示条是被替换掉，而不是单纯拿掉。**`gftv-official.md` 里那条官方网站横幅接手每一页顶上的同一个位置。它是一条窄窄的、永久的、可收起的横幅。它声明这是一个 Global Furry Television 的官方网站，并教读者怎么自己去核实。它以新加坡政府的网站抬头为蓝本。

两者绝不能同时出现。一个是临时的、可关掉的，另一个是永久的、不可关掉的，而在页头上叠两条横幅比只有其中任何一条都糟。

那个文件在各个国际兽视项目之间通用，并带着完整的规格。那就是行为、标记、取自主题变量的样式、响应式规则、无障碍，以及两种语言的文案。其中有三件事值得在这里再说一遍，因为它们是最可能被一个赶时间的实现者放软的部分：

- **它不能是可关掉的。**一条读者关得掉的横幅，就是一条他们只看一次的横幅，那就毁掉了它存在的那个教育作用。
- **它绝不能宣称这个网站是安全的或者经过验证的。**任何一个钓鱼网站都可以把这条横幅一模一样地抄过去。它唯一真正的价值是教会那条规则：国际兽视的官方网站以 `globalfurry.tv` 或 `gftv.asia` 结尾，而域名是从后面往前读的。正是那份知识，保护了一个正身处假网站的人，因为那条横幅在那里同样会出现，同样在说谎。
- **在可信网站列表那个页面存在之前，不要链过去。**一条“查看完整列表”的链接会 404 的信任横幅，比一条没有链接的还糟。
